# AI 圆桌 · 飞书桥接 + 常驻服务 技术方案

> 版本 v1.0（已落地）
> 目标：人在飞书里发一句话 → 驱动**本机常驻**的 AI 圆桌应用 → 把「7 家 AI 意见 + 1 条总结」经飞书发回。
> 形态：**常驻服务 + 飞书长连接机器人**（新建一个专属机器人）。

## 1. 背景与目标

已有 Electron 桌面应用：内嵌 7 家 AI 网页版（千问/豆包/元宝/智谱/Kimi/DeepSeek/MiniMax），复用已登录账号，广播提问 → 轮询抓取回复 → LLM 总结。

本方案不改这套核心机制，只在它外面加一层「飞书出入口」，让它能无人值守地被飞书驱动：

- 在飞书私聊机器人（或群里 @ 它）发问题
- 本地常驻服务驱动 7 个 webview 广播、抓取、总结
- 结果以飞书卡片形式发回（7 条意见 + 1 条总结）

**非目标**：不接各家官方 API、不做多轮上下文、不做账号自动登录。

---

## 2. 关键设计决策（为什么这么做）

| 决策 | 理由 |
|---|---|
| **常驻服务**（非一次性 CLI） | 7 个 webview 保持登录热状态，响应快、避免每次重载网页不稳 |
| **飞书长连接模式** | 本机无公网地址，长连接由机器人主动连出，无需内网穿透 |
| **新建专属机器人** | 本机惯例=一个服务一个 bot；避免与 cc-connect 现有 4 个应用的事件互相干扰 |
| **不复用 cc-connect** | cc-connect 面向「命令行编程 agent」，AI 圆桌是「一问→八答」，自建长连接客户端更干净 |
| **复用已登录账号** | 保住免各家 API Key 的核心优势；会话存于 `persist:` 分区，常驻进程天然复用 |

## 3. 总体架构

```
飞书客户端（你）
   │  私聊 / 群@机器人
   ▼
[新机器人 cli_xxx] ── 长连接(WebSocket，主动连出) ──┐
                                                     │
                                                     ▼
              ┌───────────────────────────────────────────────┐
              │        AI 圆桌常驻服务（Electron）              │
              │                                               │
              │  main 进程                                     │
              │   ├─ FeishuClient（@larksuiteoapi/node-sdk）   │
              │   │    · WSClient 订阅 im.message.receive_v1   │
              │   │    · 发消息 / 更新卡片                       │
              │   ├─ ServiceBridge（IPC 编排）                  │
              │   └─ 现有 webview 原语 (exec/insert/click/llm)  │
              │                                               │
              │  renderer 进程（现有 app.js 引擎）              │
              │   · broadcast → poll 抓取 → summarize          │
              │   · 7 个常驻 webview（已登录，热状态）           │
              └───────────────────────────────────────────────┘
```

- **FeishuClient** 与引擎同进程（main），收到消息后经 IPC 触发 renderer 引擎。
- 引擎沿用现有 `broadcast / pollOnce / summarize` 逻辑，GUI 同步可见进度。
- 结果回传 main，由 FeishuClient 组卡片发回飞书。

## 4. 组件设计

### 4.1 引擎封装（renderer，最小改动）

现有 `app.js` 已实现 `broadcast()` / `pollOnce()` / 总结按钮逻辑，只是由 UI 事件触发。新增一条**程序化入口**，复用同一套逻辑：

- 新增 IPC 监听：`service:ask { requestId, question }`
- 收到后调用现有 `broadcast(question)`，并在状态变化时上报：
  - `service:progress { requestId, done, generating, sending, error, total }`
  - `service:result   { requestId, summary, replies: [{id,name,state,text}] }`
- GUI 照常更新（飞书触发时桌面也能看到全过程），只是多了一条 IPC 回报通道。

> 改动原则：**不重写引擎**，只把「按钮触发」扩展为「按钮 or IPC 触发」，并增加结果回调。

### 4.2 飞书长连接客户端（main 进程）

用官方 Node SDK `@larksuiteoapi/node-sdk`：

```js
const lark = require('@larksuiteoapi/node-sdk');
const client   = new lark.Client({ appId, appSecret });
const wsClient = new lark.WSClient({ appId, appSecret });

wsClient.start({
  eventDispatcher: new lark.EventDispatcher({}).register({
    'im.message.receive_v1': async (data) => { /* 见 4.3 */ },
  }),
});
```

- 长连接由客户端主动建立，无需公网回调地址。
- 发消息 / 更新卡片用 `client.im.message.create` / `client.im.message.patch`。

### 4.3 消息处理与会话

收到 `im.message.receive_v1`：
1. **过滤**：只处理 `text` 消息；忽略机器人自己发的消息；空文本忽略。
2. **来源**：支持 P2P（私聊）与群聊 @ 机器人；记下 `chat_id` 作为回复目标。
3. **并发控制**：一次只跑一轮圆桌；若上一轮未完成，回执「正在处理上一条，请稍候」。
4. **即时回执**：先发一张「正在问 7 家… ⏳」卡片（后续用 `patch` 增量更新，避免长时间无响应）。
5. **触发引擎**：`service:ask` 带 `requestId`（可用消息 id）。
6. **收结果**：监听 `service:result` → 组装最终卡片 → 发送/更新。

### 4.4 卡片渲染（8 段内容）

8 段（7 意见 + 1 总结）文本可能很长，单张飞书卡片有体积上限（约 30KB），需控制：

- **回执卡**：问题 + 进度占位。
- **结果卡**（推荐布局）：
  - 顶部：**总结**（最有价值，完整呈现）
  - 其下：7 家意见，用卡片**折叠/分区**元素逐家展示，超长截断（如每家前 800 字）。
- **超长兜底**：若仍超限，把 7 条完整回复写入一个飞书文档或文件，卡片里放链接；总结仍放卡片。
- 失败的家在卡片中标注「失败（可桌面端手动补发）」。

> 具体卡片 JSON 结构在实现期按飞书卡片搭建器确定；本方案先定「总结置顶 + 各家分区 + 超长转文档」的策略。

## 5. 请求全链路时序

```
你: 飞书发"武汉现在适合买房吗？"
  └→ FeishuClient 收到 im.message.receive_v1
      └→ 发回执卡"正在问 7 家… ⏳"
      └→ IPC service:ask(requestId, question)
          └→ renderer broadcast(question)
              ├→ 7 家并行发送（可信输入）
              ├→ pollOnce 每 3s 抓取，陆续 done
              │     └→ IPC service:progress（更新卡片进度）
              └→ 全部完成/超时 → summarize（call-llm）
          └→ IPC service:result(summary, replies)
      └→ FeishuClient 组结果卡 → patch/create 发回
你: 收到"总结 + 7 家意见"卡片
```

## 9. 运行与部署

### 9.1 常驻运行
- 以「服务态」启动 Electron：窗口可隐藏/最小化，7 个 webview 保持 attach（已有关闭后台节流的三个开关，流式渲染不会停摆）。
- 首次需 GUI 逐家登录 7 站；登录后即可转无人值守。

### 9.2 显示环境
- 有活跃桌面会话：直接用真实显示。
- 无显示 / 锁屏需常驻：用 `Xvfb` 虚拟显示（如 `xvfb-run npm start`），`--disable-gpu` 已利于软渲染。

### 9.3 开机自启（可选，后置）
- systemd 用户服务或桌面自启动项，保证重启后服务恢复。

## 10. 风险与注意事项

| # | 风险 | 等级 | 应对 |
|---|---|---|---|
| 1 | 锁屏/无显示时 webview 渲染或抓取异常 | 🟡 中 | Xvfb 虚拟显示 + 现有防节流开关；实现期验证 |
| 2 | 8 段内容超卡片体积上限 | 🟡 中 | 总结置顶 + 各家截断 + 超长转飞书文档/文件 |
| 3 | 某家未就绪/登录失效 | 🟡 中 | 广播前检查面板 ready；失败家卡片标注，可手动补发 |
| 4 | 并发多条消息 | 🟢 低 | 单轮串行 + 忙时回执 |
| 5 | 站点改版选择器失效 | 🟡 中 | 集中在 adapters.js，维护方式同桌面版 |
| 6 | 长连接掉线 | 🟢 低 | SDK 自带重连；加心跳/重启守护 |
| 7 | App Secret 泄露 | 🟡 中 | 本地 `.env`，`.gitignore`，不入对话/仓库 |

## 11. 分阶段实施

- **Phase 0 · 准备**：建好新机器人，拿到 App ID/Secret；确认权限与长连接事件订阅（`im.message.receive_v1`）。
- **Phase 1 · 回声测试**：FeishuClient 长连接打通，收到文本消息能原样回复（验证凭证/长连接/发消息链路）。
- **Phase 2 · 引擎接线**：renderer 增加 `service:ask/result` IPC；main 收到消息能触发一轮圆桌并拿到 7 回复+总结（先以纯文本回飞书，不做卡片）。
- **Phase 3 · 卡片化**：回执卡 + 结果卡 + 进度增量更新 + 超长兜底。
- **Phase 4 · 常驻与自启**：服务态运行、Xvfb（如需）、开机自启、掉线重连。
