# AI 圆桌 · 交付说明

> 版本：v1.2（2026-08-24 修订；v1.0 于 2026-08-05 交付）
> 一句话：一个输入框，把问题同时发给 9 家 AI 网页版，收集回复并生成结构化总结。支持桌面 GUI、微信（经 Hermes skill 调本地 HTTP）两种入口。
>
> v1.2 相对 v1.0 的主要变化：**移除飞书机器人入口**（桥接代码与依赖一并删除）；**新增第 9 家 MiMo**；服务治理加固（systemd 快停/健康巡检）；HTTP 接口新增**异步模式**与参数校验。详见「八、已修复的关键坑」末尾几行。

---

## 一、系统概览

复用本机浏览器里**已登录**的 9 家 AI 网页账号（无需各家 API Key），通过网页自动化模拟真人发送、轮询抓取回复，再生成五段结构化总结。

**总结有两种模式（桌面端「设置」里切换）：**
- **网页总结（默认，免费）**：用 DeepSeek **第二账号**（独立分区 `persist:deepseek-sum`）生成总结。点「总结」时全屏展开该页面，首次需手动登录；每次总结自动开新会话，与 9 家回答流程完全隔离。各家**无删减原文 + 模板**合成 docx 以**附件形式上传**（CDP 直塞页面常驻的 `input[type=file]`，实测 accept 含 docx/md），输入框只发短指令，彻底绕开字数限制；上传不可用时自动回退为每家截断 2000 字的纯文本提示词。
- **API 总结（备选）**：任意 OpenAI 兼容接口（baseURL/apiKey/model），默认指向智谱免费模型 `glm-4.7-flash`，只需填自己的 API Key。

**9 家适配器**（`src/adapters.js`）：

| id | 名称 | id | 名称 |
|---|---|---|---|
| qwen | 千问 | kimi | Kimi |
| doubao | 豆包 | deepseek | DeepSeek |
| yuanbao | 元宝 | minimax | MiniMax |
| zhipu | 智谱 | wenxin | 文心 |
| mimo | MiMo | | |

**两种使用入口：**
1. **桌面 GUI**：直接操作窗口（输入框 + 9 家状态灯 + 总结面板）。
2. **微信（Hermes skill）**：在与 Hermes 绑定的微信里发「AI圆桌 …」触发（skill 经本地 HTTP `POST /ask` 调用，异步模式 + 轮询取结果）。

## 二、架构

```
                    ┌────────────── 桌面 GUI（输入框/按钮）──────────────┐
                    │                                                     │
                    │   AI 圆桌常驻服务（Electron，systemd 用户服务）     │
 微信→Hermes────────►│   ├─ 9 个 webview（已登录，常驻，复用登录态）      │
 (ai-roundtable     │   ├─ 引擎：广播→抓取→(陈旧检测/重试)→总结           │
  skill 调 /ask)    │   ├─ 本地 HTTP 接口 127.0.0.1:8765（同步+异步）     │
                    │   ├─ 历史记录落库                                   │
 健康巡检 timer ───►│   └─ /health 探活异常自动拉起                       │
                    └─────────────────────────────────────────────────────┘
```

- **Hermes 路径**：微信消息 → Hermes gateway 匹配 skill → skill 指引 `curl POST /ask`（`async:true`）→ 引擎 → 轮询 `/ask/status` 取 JSON → Hermes 呈现。
- **单轮串行**：同一时间只跑一轮（并发返回 429 busy），同步/异步请求共用同一 `pendingRounds` 编排。

## 五、HTTP 接口（供 Hermes skill / 集成用）

| 方法 路径 | 说明 |
|---|---|
| `GET /health` | `{ok, ready}` 探活 |
| `POST /ask` | body `{question, sites?, async?}`。同步：跑一轮返回 `{ok, question, summary, summaryError, replies[], summaryFile}`；`async:true` 时立即返回 `{ok, accepted, requestId, poll}`（202），结果经轮询取 |
| `GET /ask/status?id=xxx` | 异步轮次状态：`{state:'running'}` / `{state:'done', item:{…完整结果…}}` / 404 |
| `GET /history?limit=N&q=关键词` | 历史列表 `{items:[{id,ts,question,summary,count}]}` |
| `GET /history/item?id=xxx` | 单条完整 `{item:{summary, summaryFile, replies[]}}` |

**错误码**：`400`（缺 question / `invalid-sites`，响应附 `valid` 合法 id 列表）、`413`（body 超 1MB）、`429`（busy，正在跑另一轮**或桌面端圆桌/总结占用**）、`500`（轮次异常）、`503`（窗口未就绪）、`504`（轮次看门狗 15 分钟超时）。

示例（异步，推荐）：
```bash
# 受理
curl -sS --max-time 15 -X POST http://127.0.0.1:8765/ask \
  -H 'Content-Type: application/json' \
  -d '{"question":"一句话介绍武汉","sites":["qwen","deepseek","doubao"],"async":true}'
# 轮询（每 15–20s 一次，直到 state=done）
curl -sS --max-time 10 'http://127.0.0.1:8765/ask/status?id=<requestId>'
```

> 为何默认推荐异步：一轮最坏 ≈ 420s 轮次 + 300s 总结 ≈ 12 分钟，同步长连接几乎必然被客户端超时掐断丢结果；异步把「等待」转为「轮询」，掉线也不丢轮次（结果始终落历史库）。

## 六、使用方法

**桌面**：输入问题 → Ctrl+Enter 或「发送」（**发送后保留问题文本**）；输入框前的「＋」小按钮用于清空输入框、准备新问题。单击某家按钮全屏打开（登录/查看/补发）；是否参与在「设置」里勾选；完成后点「总结」（默认开启"全部交卷后自动总结"，>3 家交卷也可手动提前总结）。右上角按键布局：发送（左，两行高）｜总结（横跨右上）｜设置+历史（右下）。默认走**网页总结**：全屏展开 DeepSeek 第二账号页面自动生成，首次需在展开的页面手动登录（也可点总结面板标题「📋 总结」直接展开该页面，只登录不触发总结）；总结完成后回填到总结面板——正文按「一、/（一）/1./附录【家名】」分级排版，左侧目录为五段固定标签 + 「各家意见」可展开二级标签（点击展开各家，逐家跳转附录原文）。左侧家名行点击跳转总结附录对应该家原文；行尾 ↻ 仅重发该家，不影响其他家。

**微信（Hermes）**：
- `AI圆桌 问题` → 全 9 家
- `AI圆桌 只问千问、豆包 问题` → 子集，更快
- `查下之前关于 X 的圆桌` → 查历史

## 七、维护要点

### 选择器失效（最常见）
各家网站改版会导致抓取/发送失败。排查步骤：
1. 跑 `node scripts/cdp-verify.js`（需先以调试端口启动应用，Node 22+），看是哪几家 `state=error` 或抓到空/错内容。
2. 用 CDP 连进对应 webview，查真实的输入框/发送按钮/回复容器结构。
3. 更新 `src/adapters.js` 对应条目的 `inputSelectors / sendSelectors / responseSelectors`（按顺序尝试，有通用兜底）。

> 调试端口启动：`./node_modules/electron/dist/electron . --disable-gpu --in-process-gpu --ozone-platform=x11 --remote-debugging-port=9222`

### 日志
- 服务日志：`~/ai-roundtable-service.log`（HTTP/进度；超 20MB 自动截断）
- 巡检日志：`~/ai-roundtable-watchdog.log`（仅探活失败/自动恢复时写入）
- 发送失败会触发一次自动重试；仍失败则在回复中标注。
- 面板发送后 180s 抓取毫无进展会自动判「抓取超时」（错误面板可用 ↻ 补发）。

### 登录态
依赖各家网页登录。某家失效时，双击桌面端对应按钮全屏重新登录一次即可。

## 八、已修复的关键坑（供后人参考）

| 坑 | 现象 | 修复 |
|---|---|---|
| 双实例抢登录数据 | 一堆 `LOCK` 错误 | 单实例锁 `requestSingleInstanceLock` |
| 豆包/Kimi/MiniMax 抓取失败 | 网站改版，旧选择器失效 | 更新为 `md-box-root`、`.send-button-container`、`assistant-segment-active` 等 |
| **陈旧回复** | 某家本轮没答，却回了上一轮的旧答案 | 发送前抓基线，抓到与基线相同则判失败，绝不拿旧回复充数 |
| 短回复被滤掉 | "1+1=2" 这类 ≤20 字回答被跳过 | 抓取长度阈值放宽到 2 |
| `/history/item` 被 `/history` 拦截 | 单条详情返回成列表 | 路由匹配顺序调整 |
| Hermes 新 skill 不触发 | gateway 缓存旧 skill 列表 | 重启 gateway + `/new` 新会话 |
| 豆包 2026-08 再次改版 | 输入框 `data-testid` 被移除、发送按钮类名不含 `send` | 输入框改 `.semi-input-textarea`、发送按钮改 `button:has([class*="send-msg-btn"])`；问题排除改归一化模糊比较 |
| 完成判据过松 | 文本约 3 秒不变即判完成，思考前奏被当完整答案 | 判完成需连续 4 轮稳定（约 12s）；`watchStop` 家短文本且"停止生成"可见则保持等待 |
| Kimi 联网研究被误杀 | 研究数分钟无新文本，被陈旧检测判失败 | 适配器 `staleMax: 40`（约 2 分钟）；pending 清零陈旧计数 |
| Kimi 思考前奏被当答案 | 抓到思考文本就判完成 | `pruneSelectors` 排除思考/工具块 |
| 智谱长答案只剩末节 | 长答案多块只取最后一块 | 首选 `.answer-content-wrap` 整条容器；`pruneSelectors: ['svg']` 剪脑图噪声 |
| Kimi 深度研究超轮次上限 | 5~7 分钟研究被 240s 截断 | 轮次上限 240s→420s；skill curl 超时同步放宽 |
| Kimi 填了没提交（假成功超时） | 内容已填但提交报错 | 注入后校验 + 验证脚本如实报失败 + `reloadOnSendFail` 刷新重发 |
| 文心回复慢被误判失败 | 连续两轮被默认陈旧检测误判 | `staleMax: 20`（约 60s）；error 面板轮询不中断可"复活" |
| DeepSeek 输入框 id 被移除 | `#chat-input` 失效 | 改 `textarea.ds-scroll-area` 打头 |
| 总结提示词超输入框字数限制 | 8 家全文可达数万字 | docx 附件经 CDP `DOM.setFileInputFiles` 直塞隐藏 `input[type=file]`；失败回退截断文本 |
| 超短噪声被当交卷 | 文心把"通知"两字当回复 | <10 字需连续 8 轮稳定 |
| 智谱规划前奏被当答案 | 计划性前奏判完成 | pending 正则补规划类句式 |
| 子集广播清空别家回复 | 只问 2 家时其他家被清空 | 广播只重置参与面板；总结只统计 `roundScope`；↻ 单家补发 |
| Chromium 150 起抓取永远为空 | `visibility:hidden` 克隆 innerText 返回空 | 隐藏改 `opacity:0` |
| DeepSeek 2026-08-18 改版 | 发送按钮类名不含 send；附件塞入后按钮禁用窗口 | 补 `ds-button--primary.ds-button--filled`；`waitSendReady()` 轮询恢复 |
| 思考块混入抓取 | `ds-think-content` 不匹配猜测类名 | `pruneSelectors` 补真实类名 |
| 答题面板跨轮复用同一会话 | 多轮问答互相污染 | 发送前 `loadURL(adapter.url)` 开新会话 |
| 文心把按钮标签当答案 | "深度思考"4 字标签被判交卷 | `cleanReply` 噪声标签黑名单 |
| 进程崩溃无自愈 | GPU FATAL 后服务死掉 | systemd 用户服务 `Restart=on-failure` + autostart |
| 飞书入口零鉴权 | 任何会话都触发广播 | （v1.2 已整体移除飞书入口，问题随之消失） |
| 进度日志刷屏/无限增长 | 一日 1200+ 行 | 进度行去重；日志超 20MB 截断；总结 docx 保留最近 50 份 |
| 同分钟两轮 docx 互相覆盖 | 文件名时间戳仅到分钟 | 精确到秒 |
| 历史文件每次全量读盘解析 | 每次保存/查询都 load+parse | 内存缓存，仅首次读盘；写盘仍原子写 |
| **GPU FATAL 反复宕机** | `--disable-gpu` 下 GPU 进程仍启动失败（error_code=1002）→ FATAL，8-21/22/23 三次 | 追加 `--in-process-gpu`（GPU 任务并入主进程，不再派生必崩子进程） |
| **SIGTERM 挂死致停机链** | `systemctl stop/restart` 挂满 90s 才被 SIGKILL；挂起期间撞崩溃 → unit failed 不再 Restart（8-22 宕机 44 小时未自愈的诱因） | main.js 对 SIGTERM/SIGINT 显式 `app.quit()`；unit `TimeoutStopSec=15`（实测 restart 1s 完成） |
| **宕机无人知晓** | 服务挂了 44 小时无告警 | `scripts/watchdog.sh` + systemd timer 每 5 分钟探活 `/health`，异常自动拉起并记日志 |
| **千问 qianwen.com 改版抓取失效** | 发送成功且已作答（会话已建），但旧选择器抓不到，卡满 420s 不判错（2026-08-24 实测） | `responseSelectors` 首选 `.qk-markdown`/`[class*="answer-common-card"]` |
| **面板静默卡死无兜底** | 抓取空/异常不触发陈旧检测，可空转到轮次上限 | 面板活动看门狗：180s 无任何进展（非 pending 且无文本）→ 判「抓取超时」错误 |
| **未知 sites 空跑一轮** | `sites` 全无效时静默过滤，空轮还消耗总结 | 无有效 id → 400 `invalid-sites`（附 valid 列表）；部分有效取交集并告警 |
| **超大 body 无状态码** | >1MB 直接毁连接，客户端只收到 100 | 回 413 + `Connection: close`（注意：先响应后关连接，先 destroy 客户端看不到状态码） |
| **同步 /ask 超时丢结果** | 最坏 ≈12 分钟 > 任何合理 curl 超时 | 新增 `async:true` 受理即返回 + `/ask/status` 轮询；Hermes skill 已切换 |
| **cdp-verify.js 依赖回归** | 飞书依赖移除连带删掉 `ws`，自检脚本跑不起来 | 改用 Node 22 内置 WebSocket |
| **总结中间产物遗留** | `圆桌总结任务.md` 长期留在 summaries 目录 | docx 转换成功后即时删除（仅失败时保留作回退附件） |

## 九、注意事项

- **MiniMax 额度**：曾出现「积分余额不足」，额度耗尽时该家会失败，留意账号额度。
- **合规**：自动化操作消费级网页可能触碰各家 ToS，属个人自用，勿高频滥用。
- **单轮串行（GUI/服务互斥）**：桌面端与服务端共享同一引擎状态，任一侧进行中（含总结阶段），另一侧的新轮次都会被拒绝——HTTP 侧返回 429 busy，桌面侧在进度区提示。服务轮次期间桌面输入框发送与 Ctrl+Enter 均不受理。
- **网页总结（默认模式）**：总结者用独立分区 `persist:deepseek-sum`，首次使用需在点「总结」后展开的全屏页面手动登录第二个 DeepSeek 账号；登录态过期同理重登。每次总结自动从站点首页开新会话，不污染任何回答会话。原文经 docx 附件上传、无删减（回复抓取时天然限 8000 字/家）；附件机制失效时自动回退截断文本模式（每家 2000 字）。
- **总结依赖配置**：API 模式下未配总结 LLM 时总结报错（各家回复照常）；未配置时直接用默认的网页总结即可。
- **同题补发的判定边界**：对确定性问题（如"1+1=?"）点 ↻ 补发，新答案若与旧答案逐字相同，陈旧检测无法区分新旧，会判"未取到本轮回复"——此时旧答案本来就在，无实际损失；补发主要用于救治失败/垃圾答案（基线不同，判定正常）。
