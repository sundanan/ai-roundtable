# AI 圆桌 · 交付说明

> 版本：v1.0（2026-08-05 交付）
> 一句话：一个输入框，把问题同时发给 8 家 AI 网页版，收集回复并生成结构化总结。支持桌面 GUI、飞书机器人、微信（经 Hermes skill）三种入口。

---

## 一、系统概览

复用本机浏览器里**已登录**的 8 家 AI 网页账号（无需各家 API Key），通过网页自动化模拟真人发送、轮询抓取回复，再交给一个 LLM 做总结。

**8 家适配器**（`src/adapters.js`）：

| id | 名称 | id | 名称 |
|---|---|---|---|
| qwen | 千问 | kimi | Kimi |
| doubao | 豆包 | deepseek | DeepSeek |
| yuanbao | 元宝 | minimax | MiniMax |
| zhipu | 智谱 | wenxin | 文心 |

**三种使用入口：**
1. **桌面 GUI**：直接操作窗口（输入框 + 8 家状态灯 + 总结面板）。
2. **飞书机器人**：私聊专属机器人，发一句话即触发。
3. **微信（Hermes skill）**：在与 Hermes 绑定的微信里发「AI圆桌 …」触发。

## 二、架构

```
                    ┌────────────── 桌面 GUI（输入框/按钮）──────────────┐
                    │                                                     │
 飞书机器人 ─长连接─►│   AI 圆桌常驻服务（Electron）                       │
 (cli_xxx…)    │   ├─ 8 个 webview（已登录，常驻，复用登录态）        │
                    │   ├─ 引擎：广播→抓取→(陈旧检测/重试)→总结            │
 微信→Hermes────────►│   ├─ 本地 HTTP 接口 127.0.0.1:8765                │
 (ai-roundtable     │   └─ 历史记录落库                                   │
  skill 调 /ask)    └─────────────────────────────────────────────────────┘
```

- **飞书路径**：飞书消息 → 桥接（`src/feishu.js`，长连接）→ `service:ask` IPC → 引擎 → `service:result` → 发回飞书。
- **Hermes 路径**：微信消息 → Hermes gateway 匹配 skill → skill 指引 `curl POST /ask` → 引擎 → JSON 返回 → Hermes 呈现。
- **两条路径共用同一引擎与 `pendingRounds` 编排**，同一时间只跑一轮（并发会返回 busy）。

## 五、HTTP 接口（供 Hermes skill / 集成用）

| 方法 路径 | 说明 |
|---|---|
| `GET /health` | `{ok, ready}` 探活 |
| `POST /ask` | body `{question, sites?}`，跑一轮返回 `{ok, question, summary, summaryError, replies[]}`；`sites` 为可选子集（id 数组） |
| `GET /history?limit=N&q=关键词` | 历史列表 `{items:[{id,ts,question,summary,count}]}` |
| `GET /history/item?id=xxx` | 单条完整 `{item:{summary, replies[]}}` |

示例：
```bash
curl -sS --max-time 320 -X POST http://127.0.0.1:8765/ask \
  -H 'Content-Type: application/json' \
  -d '{"question":"一句话介绍武汉","sites":["qwen","deepseek","doubao"]}'
```

## 六、使用方法

**桌面**：输入问题 → Enter 发送全部；单击某家按钮切换是否参与，双击全屏登录/手动补发（手动判定 400ms 容错）；完成后点「总结」（设置里可开"全部交卷后自动总结"）。左侧家名行点击跳转总结附录对应该家原文；行尾 ↻ 仅重发该家，不影响其他家。

**飞书**：私聊机器人发「问题」即可；回复为摘要文本 + 总结 docx 附件（五段结构：主要共识/次要共识/分歧观点/个性观点/综合意见，附录含各家原文；docx 生成或发送失败时回退纯文本逐家摘录）。

**微信（Hermes）**：
- `AI圆桌 问题` → 全 8 家
- `AI圆桌 只问千问、豆包 问题` → 子集，更快
- `查下之前关于 X 的圆桌` → 查历史

## 七、维护要点

### 选择器失效（最常见）
各家网站改版会导致抓取/发送失败。排查步骤：
1. 跑 `node scripts/cdp-verify.js`（需先以调试端口启动应用），看是哪几家 `state=error` 或抓到空/错内容。
2. 用 CDP 连进对应 webview，查真实的输入框/发送按钮/回复容器结构。
3. 更新 `src/adapters.js` 对应条目的 `inputSelectors / sendSelectors / responseSelectors`（按顺序尝试，有通用兜底）。

> 调试端口启动：`./node_modules/electron/dist/electron . --disable-gpu --ozone-platform=x11 --remote-debugging-port=9222`

### 日志
- 服务日志：`~/ai-roundtable-service.log`（飞书/HTTP/进度）
- 发送失败会触发一次自动重试；仍失败则在回复中标注。

### 登录态
依赖各家网页登录。某家失效时，双击桌面端对应按钮全屏重新登录一次即可。

## 八、已修复的关键坑（供后人参考）

| 坑 | 现象 | 修复 |
|---|---|---|
| 双实例抢登录数据 | 一堆 `LOCK` 错误 | 单实例锁 `requestSingleInstanceLock` |
| 豆包/Kimi/MiniMax 抓取失败 | 网站改版，旧选择器失效 | 更新为 `md-box-root`、`.send-button-container`、`assistant-segment-active` 等 |
| **陈旧回复** | 某家本轮没答，却回了上一轮的旧答案 | 发送前抓基线，抓到与基线相同则判失败，绝不拿旧回复充数 |
| 短回复被滤掉 | "1+1=2" 这类 ≤20 字回答被跳过 | 抓取长度阈值放宽到 2 |
| `/history/item` 被 `/history` 拦截 | 单条详情返回成列表 | 路由匹配顺序调整 |
| Hermes 新 skill 不触发 | gateway 缓存旧 skill 列表 | 重启 gateway + `/new` 新会话 |
| 豆包 2026-08 再次改版 | 输入框 `data-testid` 被移除、发送按钮类名不含 `send`；消息能发出（兜底 Enter）但抓不到答案，或把排版后的问题回音当答案 | 输入框改 `.semi-input-textarea`、发送按钮改 `button:has([class*="send-msg-btn"])`；问题排除改为归一化（去空白/标点）模糊比较 |
| 完成判据过松 | 文本约 3 秒不变即判完成，智谱思考前奏、MiniMax 搜索前奏、豆包问题回音被当完整答案 | 判完成需连续 4 轮稳定（约 12s）；适配器 `watchStop: true` 时，短文本且"停止生成"按钮可见则保持等待 |
| Kimi 联网研究被误杀 | 研究数分钟，期间无新回复文本，默认陈旧检测约 24s 判"未取到本轮回复"，实际稍后已答完 | 适配器 `staleMax: 40`（约 2 分钟）；pending 状态清零陈旧计数。研究超过轮次上限（现 420s）仍可能丢，属已知边界 |
| Kimi 思考前奏被当答案 | 抓到"用户问的是…需要搜索…"的思考文本就判完成 | 适配器 `pruneSelectors`（`.thinking-container`、`toolcall-container`）：收集与剪枝两层排除思考/工具块；剪完无内容则继续等待真实答案 |
| 智谱长答案只剩末节 | 长答案拆成多个 `.markdown-body` 块，"取最后一块"只拿到末节（曾 5877 字答案只抓到 307 字的第九节）；自动生成脑图的 svg 节点标签也混进 `[class*="markdown"]` 命中 | 智谱适配器首选 `.answer-content-wrap` 整条答案容器；`pruneSelectors: ['svg']` 剪掉脑图噪声 |
| Kimi 深度研究超轮次上限 | 复杂问题 Kimi 自动深度研究要 5~7 分钟，旧上限 240s 到点时仍在生成，该家记失败丢答案 | 轮次上限 240s→420s（`waitForRoundComplete`，全部到终态会提前返回）；Hermes skill 的 curl `--max-time` 320→460 同步放宽 |
| Kimi 填了没提交（假成功超时） | 输入框已填入但未提交，手动提交报错，手动刷新+重贴后可发；旧逻辑 `via: 'unverified'` 把没验证当成功，只能等陈旧检测约 2 分钟兜底，表现为"超时" | 三层加固：① 可信注入后校验内容真进了编辑器，没进则重新聚焦再注入一次；② 验证脚本确认"内容仍在输入框"时如实报失败（仅验证脚本本身失败才兜底放行）；③ Kimi 适配器 `reloadOnSendFail: true`：发送失败后自动刷新 webview 重发一次 |
| 文心回复慢被误判失败 | 文心明显偏慢，连续两轮先被陈旧检测（默认约 24s）判"未取到本轮回复"，稍后实际交卷 | 文心适配器 `staleMax: 20`（约 60s）；error 面板轮询不中断，迟到回复仍可"复活" |
| 超短噪声被当交卷 | 文心把页面"通知"两字当回复（长度阈值 ≥2 放行） | 回复 <10 字时要求连续 8 轮稳定才判完成（正常回复 4 轮） |
| 智谱规划前奏被当答案 | 抓到"用户想玩两天…需要补充最新信息"这类计划性前奏就判完成 | pending 正则补充规划类句式（`需要补充`、`^用户(想\|问\|需要)`），命中且短文本时继续等待 |
| 子集广播清空别家回复 | 只问 2 家时，其他 6 家上一轮回复被 `p.reply=''` 清空 | 广播只重置参与面板；总结也只统计本轮范围（`roundScope`）；新增行尾 ↻ 单家补发（复用 `runSendTask`） |

## 九、注意事项

- **MiniMax 额度**：曾出现「积分余额不足」，额度耗尽时该家会失败，留意账号额度。
- **合规**：自动化操作消费级网页可能触碰各家 ToS，属个人自用，勿高频滥用。
- **单轮串行**：服务同一时间只跑一轮，重复请求返回 busy。
- **总结依赖配置**：未配总结 LLM 时，各家回复照常但总结报错。
- **同题补发的判定边界**：对确定性问题（如"1+1=?"）点 ↻ 补发，新答案若与旧答案逐字相同，陈旧检测无法区分新旧，会判"未取到本轮回复"——此时旧答案本来就在，无实际损失；补发主要用于救治失败/垃圾答案（基线不同，判定正常）。
